# Physical-device acceptance plan

All cases are **NOT RUN** at creation. Use expendable or separately backed-up test clips, starting on the iPhone 15 Pro Max. No test removes an original except the two deletion cases at the end, which remove one expendable original each and only after you have turned deletion on yourself. An installed internal build and a passing simulator test suite are prerequisites, not proof of the media pipeline.

These cases were written against the source at commit `07526c4`, and were extended by five rows - the free-space gate, the bounded format read, the read-back after a save, the scrub sheet's player item and a retrieval Photos cancels by itself - in the rounds after `4d5da93`. Build 10 (`0.1.0`) is the last build known to have run anywhere, and it predates the round 1 queue, deletion and verification changes and every round after them, so a pass against build 10 covers none of this. **The build that carries all of it has not been made yet**: `app.json` names build 11 for the next upload and no upload with that number exists, so whether the first run of this plan is build 11 or a later number is a commitment rather than a fact - write down the number and the commit the build was made from, and treat every result below as evidence about that build and no other. Nothing since build 10 has been installed on a device, so the first run of this plan is the first evidence about any of it.

**What has changed under this plan since it was written, so a tester meets what is actually there.** These are the round 8 to 24 changes that touch a step below; nothing here removes a case, but some of them change where a control is or when something happens.

- **First launch shows an introduction first.** A fresh install opens on three pages with `Continue`, then `Get started` on the last page, and `Skip` in the top corner. The home screen is behind it. A pass that starts from an existing install does not see it; one that starts from a clean install must get past it before any control in the rows below exists.
- **Photos access is asked for when the user scans or chooses a video, not at launch.** The app's own introduction promises this. Round 19 fixed the launch path that had been opening the system permission alert before the user asked for anything, and the fix is unverified Swift, so a device run should confirm both halves: nothing is asked on launch, and the first scan or picker does ask.
- **The single-video control is `Choose a video`** (then `Choose another video`); the batch flow's primary control is `Find my videos`. There is no control simply called Choose.
- **The finished screen's extra actions are behind a `More actions` menu.** The bar itself is `Shrink more videos` and `Done`; deleting originals, retrying the failed ones and re-running checked-in-Photos items are menu items rather than separate buttons. Any batch case that reaches for one of those three must open the menu first.
- **Each flow owns its own temporary directory** (`VideoShrink-Phase0` for the one-video flow, `VideoShrink-Phase0-batch` for the batch), so finishing a batch no longer removes an unsaved one-video copy. A cleanup inspection should find only the directory belonging to the flow that ran.
- **Estimate and summary wording moved** (round 19): the headline counts only the videos the estimate expects to get lighter, "copies about" counts only the originals a copy is expected for, the confirmation before a run says "at up to" a size, and a per-video storage refusal names the figure it needed. Record what the screen actually said rather than checking it against an older string.
- **The suite has grown well past the 162 cases that first ran** (the local gate prints the current count), and it has not run since the runners stopped starting on 2026-09-23. A green suite is a prerequisite for this plan, not a result in it.
- **The selection screen names the videos Select all will leave alone** (rounds 21 to 24). A video whose copy the app could not account for is listed under the heading `Left out of Select all`, with the question about it and a hint that ticking it by hand is how to choose it anyway. `Select all` can therefore come out lower than the number of videos on screen, and the number it leaves out is deliberate rather than a fault.
- **A saved run's record that cannot be read says so** (round 23). The start screen and the selection screen draw a notice headed `A saved run couldn't be read`: nothing was restored from that record and nothing in Photos was changed, and the notice comes back on every launch until a run writes a record of its own. Nothing on a phone can make a record unreadable, so this one is met rather than made: if you ever see it, write the exact words down and look through Photos for a second copy of anything this app ran before that launch.
- **Closing the video picker without choosing returns to the welcome screen** (round 23), with a usable `Choose a video`, rather than to a recovery screen written for a run that had ended.

Record: app version/build, Git revision once available, iOS/Xcode versions, device, permission mode, codec/resolution/HDR/frame rate, duration, audio, network/power/thermal conditions, source/output byte counts, observed outcome and pass/fail. Do not put private filenames, library identifiers, locations or personal footage in the repository.

**Original safety is written on each case that changes Photos.** Every case below that saves a copy
or removes an item ends with its own `Original safety` line, and that line is the same check every
time: before the case, note the original's item, dimensions, duration, visual quality and edit state;
after it, compare them, and confirm nothing was moved to Recently Deleted unless the case is one of
the two that delete. The `Original safety` row at the end of the table keeps only the checks that
belong to no single case.

## First five tests

1. **Local landscape video with audio:** choose a short, unedited, high-bitrate SDR clip already downloaded. Verify sensible measured metadata, export progress and ready-to-save state. Preview beginning/middle/end and listen. Confirm exactly one new Photos item appears only after Save; original duration, quality and edit state remain unchanged. Original safety: before and after.
2. **iCloud-only original:** use a known offloaded, expendable clip with Optimize iPhone Storage enabled. There is no reliable public “evict just this original” action in this app; do not assume an asset is cloud-only just because optimization is enabled. Record how offloaded status was established. Look for PhotoKit download progress, complete the pipeline and save. Repeat with connectivity unavailable to observe a clear retrieval failure. A cached original can still succeed offline, so that is not proof of an iCloud path. Original safety: before and after.
3. **Portrait video with audio:** compare orientation and aspect in preview and in Photos after import, including rotation/fullscreen playback. Check audio synchronization near both ends and confirm the measured size reduction is positive. Original safety: before and after.
4. **Cancel while transcoding:** use a sufficiently long 4K clip, cancel after real progress begins, and confirm no new Photos item, cancelled status and a usable fresh selection. Repeat selection/export to expose stale callbacks or leftover output.
5. **Long 4K HDR video:** choose the clip in the one-video flow and again in a batch run. An HDR original is refused by name once the app has read the video's own format, so the expected result is a refusal and no copy: write down the exact sentence and where it appeared - the listing's refused list, the pre-flight read before a run starts, that video's own row in the run, or, in the one-video flow, the screen the flow stops on. Do the same with a ProRes clip, which is refused the same way. There is no HDR copy to compare brightness against; a copy offered for either clip is the failure this case exists to catch, and Photos should have no new item for it afterwards.

## Full matrix

Several of the rows below are about what the app decides with, what it waits for, and how it reacts when the
system answers it with a cancellation, rather than about the media pipeline itself. None of them can be
settled on a simulator.

The free-space gate is a heuristic in all three places it fires - before a retrieval, before an export and
before a save - and it compares a figure the app computes against what the volume reports as available for
important usage; the write itself stays the real report. Every call site now sizes its step with
`DiskHeadroom.neededToWrite(_:)`: the one file the step is about to write, plus the reserve. That is the
question a space check should be asking, because the file a step is copying from is already on the disk and
already reflected in the free space the check reads, so counting it again demands room the step never needs
and turns away a phone with room to finish. The older two-copy arithmetic, `DiskHeadroom.bytes(_:copies:)`,
has no production caller left; it survives only because its arithmetic is pinned by test, and its own doc
comment in `BatchModels.swift` is the only place still worded as though the export checks used it. The
reserve itself has never been measured on a device, and a video smaller than the reserve can be refused for
want of room that the file itself would not have needed; only a device can say whether 256 MB is the right
margin.

## Reset, deletion and a killed save

These cases come last, and the reset comes before them, because two of them can leave something behind
that changes what a case above would mean: a batch run with deletion on removes the originals whose
copies it confirmed, not only the video a case is about, and a save the app was killed inside of can
leave a copy in Photos that nothing has written down.

**A run with deletion on removes originals, in either of its two deleting modes.** `Delete as it goes`
removes each original as soon as its copy is saved and checked, so Photos' own confirmation can appear
in the middle of the run; `Delete at the end` waits until the run has finished and then removes every
original that qualified, behind one confirmation from the app and one from Photos. Both put the
originals in Recently Deleted, where they stay for 30 days. So turn deletion on from the batch flow's
`Originals` row, which asks you to confirm the mode itself, for the cases here only - with one
expendable video in the run unless the case says otherwise - and turn it back to `Keep every original`
afterwards.

6. **Reset between cases:** delete the copies the earlier cases left in Photos, and any original you no longer want. Open Recently Deleted and delete them there as well if you want the space and a clean count back, because Photos holds them for 30 days otherwise. A completely fresh app means deleting and reinstalling it: the app keeps its own record of a run it stopped inside, and of the copies it has made, and only a reinstall removes all of that. Finishing a run and tapping `Done` clears that run's own record, but a question the run could not answer is kept on purpose until you answer it. Leave deletion on `Keep every original` unless the case you are about to do turns it on itself.
7. **Kill a save in a batch run:** do the export half first. Start a run with one expendable video, force-quit while it is exporting, reopen, and confirm the run comes back with that video waiting to be run again rather than reported saved. Then do the save half: run it again and force-quit while that video's copy is being handed to Photos - the working screen says it is saving and asks you to wait for Photos to confirm. Reopen the app. The copy's receipt is written only once Photos has answered, so the app can rarely settle this one, and the video should come back as a question: the restored run's own screen draws a row for it, and the selection screen lists it under the heading `Left out of Select all` with a sentence saying the app cannot tell whether a copy was made. Sometimes the app can settle it instead - it finds the copy and records it as its own output so it is never run again, or it sees the whole library and finds no copy and the video waits to be run - and then no question is left. Write down which you got and the wording the app used. Then, whichever it was, open Photos and count the copies of that one video for yourself: two copies means Photos committed a save the app died inside, one means it did not, and that count is the only evidence there is, because the app's own answer comes from the same look this case exists to test. Original safety: before and after.
8. **Kill a save in the one-video flow:** choose one expendable video, get it to the ready-to-save screen and tap `Save copy to Photos`, then force-quit the app while the bar is waiting for Photos to confirm. Reopen the app and start a batch selection: that video should be named under `Left out of Select all` with the question about a copy that may or may not have been made, and `Select all` should not tick it. Then open Photos and count the copies as above, and write the count down. This flow's note is written into the app's own store immediately before it asks Photos for a copy, and whether it survives a kill is exactly what nobody can tell from the source - so record whether the video was still named after the relaunch, which is what the note is for. One more observation belongs to this flow, and it holds whether or not the save was killed: after a one-video save that reports success, the batch selection screen is where you can see what the app wrote down. The *original's* tile should read `Previously shrunk` - the app marks it as a video this iPhone has shrunk on either answer from Photos, so that `Select all` leaves it alone instead of making a second copy of it - and the *copy's* tile reads `Made by BatchShrink` only when Photos named the copy as it handed it back. Neither tile reading `Made by BatchShrink` therefore means Photos finished the save without handing an identifier back; write down both captions. Those two tiles are hard to tell apart because the copy keeps the original's filename and date. Original safety: before and after.
9. **Decline Photos' own confirmation:** turn deletion on - `Delete at the end` is the easier one, because the run finishes before anything is deleted - and take one expendable video through a batch run so that its copy is confirmed and the original qualifies. Finish the run, open `More actions` and choose the item that deletes the originals, then accept the app's own question. Photos asks its own confirmation of the same deletion: decline it. Write down everything the app says about that original. The video's row is where the app records it: either `original kept` followed by a reason, which is the wording for a refusal the app made itself, or the shorter `original is still here` with no reason, which is what it writes when Photos' answer was an error or a cancellation. A decline and a real failure produce the same short sentence, so what a phone can settle here is whether the app said the original was kept or claimed a deletion that did not happen - not which of those two Photos' answer was. Then open Photos: the original should still be in the library and should not be in Recently Deleted. Original safety: before and after.
10. **Accept Photos' own confirmation:** do it again - with two expendable videos in the run if you can spare them - and accept Photos' confirmation this time. That video's row should say its original was deleted, and the finished or paused screen should say the original sits in Recently Deleted for 30 days, which is also when the space comes back. Then open Recently Deleted in Photos and count: every original the run said it deleted should be there, and any that is missing is a deletion the app reported and Photos did not make. With two videos this also answers whether Photos removes a whole batch at once, because the app reports every original it asked about: write down how many of the two actually went. Original safety: before and after.

## Evidence and pass criteria

Use a results sheet outside this repository if it contains personal information. For each case record observed facts, not “looks okay.” Store sanitized failures and exact reproduction steps in an issue or a future `docs/DEVICE_RESULTS.md`.

Phase 0 passes only when the iCloud retrieval → **a smaller copy** → verification → separate Photos save path works on the physical iPhone and the original is unchanged. Record the codec you actually got: the 720p quality produces H.264, and 1080p and 4K produce HEVC, so "smaller HEVC output" is one shape of a pass and not the test. HDR and ProRes originals are refused rather than copied, background behavior needs its own result, and passing SDR does not certify any of them. Pause expansion into batching until safety failures are understood and corrected.
